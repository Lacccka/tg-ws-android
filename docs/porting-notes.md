# Porting Notes

## Repository rules

1. Never edit `third_party/tg-ws-proxy` directly. Treat it as the upstream source
   of truth and update it only through normal git submodule operations.
2. Every ported Kotlin class must mention the upstream Python file and function
   or class it mirrors in a KDoc comment near the class declaration.
3. All critical logic must have parity tests against Python-generated vectors
   before it is considered ported.
4. Do not mix unrelated upstream ports in one change. Prefer small commits that
   update one mapped module and its parity vectors.
5. If `tools/check_upstream.py` reports a changed hash, inspect the upstream diff
   before editing Kotlin code and record any required porting work in the commit
   or PR summary.

## Current scope

The Android structure now includes runtime configuration plus offline parity
ports for MTProto handshake, relay init, crypto context, MsgSplitter, and the
RawWebSocket frame/request/response codec. TCP server wiring, socket bridge, live
WebSocket/TLS networking, fake TLS, pooling, foreground service integration, UI,
and balancing code remain intentionally unimplemented until their own parity or
integration test scopes exist.

## Parity-test workflow

1. Generate vectors from the exact submodule revision recorded in git.
2. Store vectors under a future test-vector directory with enough metadata to
   identify the upstream file/function and submodule commit.
3. Add Android unit tests that compare Kotlin outputs with the Python-generated
   vectors.
4. Run `python3 tools/check_upstream.py` in every porting change to detect
   upstream drift.

## MTProto handshake vectors

`app/src/test/resources/handshake_vectors.json` is generated by
`tools/generate_handshake_vectors.py` from the checked-out upstream
`proxy/tg_ws_proxy.py::_try_handshake` implementation and constants in
`proxy/utils.py`. Regenerate these vectors after any relevant upstream change
before updating the Kotlin parser so parity failures are attributable to the
upstream diff.


## Relay init and crypto context vectors

`app/src/test/resources/crypto_vectors.json` is generated by
`tools/generate_crypto_vectors.py` from upstream
`proxy/tg_ws_proxy.py::_generate_relay_init`,
`proxy/tg_ws_proxy.py::_build_crypto_ctx`, `proxy/bridge.py::CryptoCtx`, and
constants in `proxy/utils.py`. Regenerate these vectors after any relevant
upstream change before updating `RelayInit` or `CryptoContext`.

`RelayInit` supports deterministic random-byte injection only so unit tests can
replay upstream `os.urandom` calls exactly. Production code uses secure
randomness by default and should not pass deterministic providers.


## Message splitter vectors

`app/src/test/resources/splitter_vectors.json` is generated by
`tools/generate_splitter_vectors.py` from upstream
`proxy/bridge.py::MsgSplitter` and transport constants in `proxy/utils.py`.
Regenerate these vectors after any relevant upstream splitter or transport
constant change before updating `MsgSplitter`.

The splitter is stateful: it advances an AES-CTR stream, keeps ciphertext and
plaintext buffers across `split(...)` calls, and returns original ciphertext
packet boundaries. Vector cases intentionally preserve chunk boundaries because
different chunking can exercise different internal AES-CTR and buffer states even
when the concatenated bytes are identical.


## RawWebSocket offline vectors

`app/src/test/resources/websocket_vectors.json` is generated by
`tools/generate_websocket_vectors.py` from upstream
`proxy/raw_websocket.py::RawWebSocket._build_frame`,
`proxy/raw_websocket.py::RawWebSocket._read_frame`,
`proxy/raw_websocket.py::RawWebSocket.connect`, `WsHandshakeError`, and
`_xor_mask`. Regenerate these vectors after any relevant upstream
`raw_websocket.py` change before updating `RawWebSocketCodec`.

Only the offline codec/request/response behavior is ported here: frame
construction and parsing, mask/unmask behavior, HTTP Upgrade request text, and
practical status/header parsing for handshake responses. Live TLS sockets, real
WebSocket connections, TCP server integration, Android networking, bridge logic,
foreground services, and UI work are intentionally left for separate milestones.
